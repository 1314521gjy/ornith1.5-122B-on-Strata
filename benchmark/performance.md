## §2 判否清单（全部带判据）

### 2.1 假设错（直觉不对）

| 项 | 结论 | 判据 |
|---|---|---|
| **MTP 投机 window 8（带 DET）** | **−52.0%** | `right=k/7` 证明窗口生效；tokens/round 只从 2.0 涨到 2.1，而 ms/round 21→117、acceptance 33%→15% |
| **强制满仓投机（`STRATA_DET_WINDOW=1`）** | **−24%**（同参数的自适应版是 **+6.2%**） | 两种算法，不是同一件事的噪声 |
| **排序键改纯计数** | **0.000pp** | 48 层 expert 形状全等、槽字节同一常数 ⇒ `/字节` 不改变排序 |
| **补表长到 100%** | **0.000pp** | 第 6,103 名 count=8，新增 prior=0 的进不了 top-N |
| **换负载重学表（agent 轨迹）** | **0pp** | 新表 +34% 大小，held-out 命中 80%→80% |
| **`CPU_KERNELS`** | **结构性不触发** | 只接 `Q4_K + 非门控`；本模型 IQ3_XXS + 门控 |
| **`STRATA_MMVQ_IL`** | **默认已开**（不是杠杆） | `verify.cpp:159` `v==nullptr \|\| v[0]!='0'` |
| **连带预取（共现驱动）** | **判死（字节级）** | 共现 lift 最高 78.88 但它是"同 token 内"结构；union k=2 需 1,701 MB/token = 当前 DMA 的 **10.9×** ⇒ 光搬运 72.7 ms vs 整条 decode 20.1 ms |
| **DFlash** | **无对象** | 899 张量 + 51 KV + 7 仓 config 全 0 命中；有 MTP 无 DFlash |
| **位精确对拍** | **不可达（默认配置）** | 同 exe/config/prompt/temp=0 两次跑输出不同；根因 `--expert-swaps` 异步迁移；只在 `--expert-swaps 0 --lookup 0` 下可复现 |

### 2.2 不划算（方向对、成本过高）

| 项 | 结论 | 判据 |
|---|---|---|
| **T8 跨层双缓冲** | **−18.5%** | 机制跑通（L3 行 5 条、staging 1×、`hold reuses` 恒 0）但 chunk 放大让"多 call"前提消失 |
| **`--expert-swaps 0`** | **−40.6%** | 命中 89%→61.8%（关掉交换后 decode 期新专家不再迁入） |
| **`--pcie-frac 1.0`** | **decode 中性** | 真生效（`pcie=43.24 experts/token`）但 `0 direct`、CPU 腿与 PCIe 腿成本相近 |
| **融合 DMA（捆绑搬运）** | **无收益** | 上游实测提交 −82.7% 但总传输 −1.3%、30.3 vs 30.0 tok/s |
| **簇级缓存准入** | **判死** | 61 硬簇只覆盖 1.99% 流量；模拟实测**为负**；天花板 0.018 ms/token |
| **行回收（治 −7% 缓存漂移）** | **判否（问题消失）** | PF-F 下 8K prompt 不再触发任何缩容（A 组 5×短 = 5,544×5、B 组 1×8K+5×短 = 5,544×6） |
| **`pb4096`** | **淘汰** | prefill 1954.6 ✓ 但 decode 45.70 < 46.5 |
| **变长槽位** | **拿不到** | 收益要求每 (layer,expert) 字节**不同**；本模型统一 3.586 MiB/专家 |
| **`env 四联`（swap 直拷/pool spin/borrow）** | **无收益/不适用** | 三臂噪声内；borrow 报 `920 MiB … only 663 MiB can be lent` |
| **`--prefill auto` / `PF_FUSED`** | **不存在** | `src/poly` 全量 0 命中；`strata-poly` 链接面不含 `strata_prefill` |
| **`ROUTE_PRIOR`（超级极速）** | **no-op** | `verify.cpp:1502` 硬要求 `NE==512 && K==10`；本模型 256/top-8 |

## §3 三条方法论（比读数更值钱）

### 3.1 判否会过期

一个判否的成立条件一旦改变（exe / 配置 / env / 硬件状态），判否就**自动失效**。
**实例**：`--prompt-batch 4096` 判过 **−3.03%**，那是「旧 exe + 无 pin + RING2 白占 918 MiB」下测的；之后三个条件全变，同一个值变成 **+41.8%**。
**要求**：台账里每个判否必须记「测它时的 exe / 配置 / env / 硬件状态」。

### 3.2 对拍要参数级，不是机制级

机制级对照能扫出「他们有 chunk」，**扫不出「他们 8192、我们 2048」**。
六层全扫：**① 参数（值差、开关有无）② 机制（有没有）③ 架构（几何折算，裸数字不可比）④ 源码实现（同一机制两边怎么写）⑤ 理论（公式能否复算）⑥ 运行（实测 + 测时条件）**。
**铁律**：上层看不见下层 —— 机制层扫不出值差。

### 3.3 零改码优化会抢跑改码优化

本轮两个改码项都被零改码项"抢跑"：
- **T8**：17 落点 + 两次编译 + 修 bug ⇒ **−18.5%**（chunk 让"多 call"前提消失）
- **行回收**：30–45 行方案 ⇒ **问题消失**（chunk 让"缩容"行为消失）

⇒ **动改码前，先确认零改码那一层已经吃干净。**

## §4 数据口径（踩过的坑）

| 坑 | 表现 | 判据 |
|---|---|---|
| **`reused=4096`** | prefill 假高约 2× | 引擎每 4,096 token 存检查点，只改 prompt 末尾会走混合路径 ⇒ 真值 1030 报成 2004。**只认 `reused=0`，唯一标记放 prompt 最前面** |
| **短答案** | decode 系统性低估 30~40% | 5~7 token 的答案把 ~50 ms/请求的固定开销摊在极短窗口上。**要 150~250 字的长答案** |
| **`max_tokens` 被 thinking 吃光** | content 0 字 + `finish=length` | `usage` 里 thinking **计入 `completion`**、无 `reasoning_tokens` 字段。**开思考时 `max_tokens` ≥ 4096** |
| **`pcie_us/miss`** | 假绿判据 | 量的是主机侧 `cudaStreamWaitEvent` 入队耗时（恒 ~0.2 µs）；另一处是 `main.cpp:921` 的死字面量 |
| **引擎 run-to-run 不可复现** | 位精确判据失效 | 同 exe/config/prompt/temp=0 两次跑输出不同（`约130次` vs `约75次`）；根因 `--expert-swaps` 异步迁移 |
